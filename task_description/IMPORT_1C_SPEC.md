## 1. Бізнес-процес (з твоїх слів)

- Водій щоденно бере накладну, сканує QR-код → на боці системи вже є
  `RouteEvent` з `waybill_number` + `waybill_date` (Фаза 3.7/8, вже
  реалізовано).
- Раз на тиждень **менеджер-операціоніст** в офісі заходить на сторінку
  сайту, обирає файл(и) вивантаження з 1С і завантажує його.
- За потреби — можна **перевантажити конкретний день**: старі записи за
  ту юрособу видаляються, нові з файлу записуються натомість.
- Джерела — три юридичні особи, кожна зі своїм форматом вивантаження:
  - **РУБІН** — `SalesLineItem_history.csv` (класичний реєстр продажів).
  - **ЄСП** — `Переміщення зі складів на АЗС.xls` (переміщення зі
    складу на точку).
  - **ОПТ** — аналогічний до ЄСП `.xls`-файл, за словами користувача
    відрізняється тим, що там ~8 реальних АЗС замість 2 складів.

**Важлива корекція від початкового припущення:** оскільки менеджер
завантажує файл **на сторінці сайту**, це не суто CLI
`management command` — потрібен upload-ендпоінт на бекенді + форма на
фронтенді (`vehicle_cost_tracker`, маршрут `/waybills/import` вже
заведений як `PlaceholderPage` в `App.tsx`). Бекенд можна зробити й
перевірити незалежно від React-форми (Postman/DRF browsable API), але
без форми завантаження вручну менеджер файл не заллє.

## 2. Файл 1 — `task_description/file_1C/SalesLineItem_history.csv` (РУБІН)

- Кодування: **`cp1251`**, роздільник `;`, значення в лапках, десяткові
  через крапку.
- Заголовок (15 колонок):

  ```
  customer_id;customer_name;date;invoice_number;line_number;store_address;
  product_id;product_articl;product_name;quantity;price_invoice;
  line_total;comment;contract_name;doc_type
  ```

  - Приклад рядка (декодовано):

    ```
    customer_id     = "000000333"
    customer_name   = "ТОЛІМАН ПЛЮС ТОВ"
    date            = 2026-08-17          # ISO, без лапок
    invoice_number  = "РБН00008425"     # у водія відсканований 8425
    line_number     = 1.00
    store_address   = "м. Харків, вул. Плиткова, буд. 12"   # текст адреси, НЕ id
    product_id      = "000000143"         # внутрішній 1С-ID (РУБІН)
    product_articl  = "49907"             # артикул є спільним для РУБІН, ЄСП, ОПТ
    product_name    = "Винний напій аром. газ. Bellini..."
    quantity        = 360.00
    price_invoice   = 60.00
    line_total      = 21600.00            # = quantity × price_invoice
    comment         = "0674264722 Тімченко Андрій Петрович"
    contract_name   = "Вино"
    doc_type        = "sale"
    ```

- `doc_type` — у переглянутій вибірці бачив тільки `"sale"`. За словами
  користувача, повернення позначаються **від'ємною `quantity`**, а не
  окремим `doc_type` (треба підтвердити — сам не знайшов жодного
  від'ємного рядка у вибірці, яку переглядав).
- `store_address` — це **вільний текст адреси**, не `id_store` з
  `01_PROJECT_OVERVIEW.md` §6.5. Прямого відповідника до `Store.id_store`
  у файлі немає шукаємо по назві в Store.

## 3. Файл 2 — `task_description/file_1C/Переміщення зі складів на АЗС.xls` (ЄСП)

- Справжній legacy `.xls` (BIFF/OLE2), для читання знадобився `xlrd`
  (у venv його не було — `xlrd==2.0.1`, він єдиний з актуальних, що ще
  вміє читати старий `.xls`; `pandas`/`openpyxl` теж не стояли).
- Один аркуш, **39579 рядків × 13 колонок**. Заголовок — рядок 1
  (рядок 0 — службовий "Печать таблицы значений").
- Колонки (оригінальні назви з 1С, російською):

  ```
  № | Магазин | ДатаДок | Докум | Категория | Код | Товар |
  Количество | ЦенаВх | СуммаВх | СуммаР | КоличВупак | Вес
  ```

- Приклад рядка:

  ```
  Магазин      = "Склад Вино БЦ"
  ДатаДок      = "19.08.26"                          # DD.MM.YY
  Докум        = "ПеремМежМагазРасх 0000401034"      # у водія відсканований 0000401034
  Категория    = "РубинЗаказ"
  Код          = 23761                 # артикул є спільним для РУБІН, ЄСП, ОПТ     
  Товар        = "Напій Fragolino ігр. вино біле 0,75л"
  Количество   = 6.0
  ЦенаВх       = 108.78                              # закупівельна ціна/од.
  СуммаВх      = 652.68                               # = Количество × ЦенаВх
  СуммаР       = 1199.94                              # роздрібна сума (вища за СуммаВх)
  КоличВупак   = 6.0                                  # шт. в упаковці
  Вес          = (у прикладі порожньо в цьому рядку)
  ```

- **`Магазин`** — лише 2 унікальних значення в цьому файлі:
  `"Склад Вино Ужгород"` (173 рядки) і `"Склад Вино БЦ"` (39403 рядки).
  Обидва — **склади**, жодної реальної АЗС тут немає (на відміну від
  ОПТ-файлу, за твоїми словами — там ~8 АЗС). Останній рядок файлу —
  службовий підсумок `"ИТОГО:"`.
- **`Категория`** (50 унікальних значень) — судячи з вмісту
  (`Bounty`, `Twix`, `Mars`, `Кока-Кола`, `БРСМ TURBOTA PRO ЛЮДЕЙ`,
  `Auchan`, `МЕТРО`, `РубинЗаказ`, `Рубин Китай`, `СП Юкоил`,
  `ТАЙМАВТО`...) — **це категорія/бренд товару**, не клієнт: товари
  одного бренду йдуть підряд одним блоком рядків. `РубинЗаказ`/
  `Рубин Китай` там теж лише назви категорій — не міжкомпанійський
  трансфер (треба підтвердити).
- Дат — 170 унікальних, діапазон приблизно 01.03.26 — 19.08.26.
- Жодного рядка з від'ємною `Количество` не знайшов (перевірив усі
  39579 рядків).
- **`Код` (23761) збігається з `product_articl` (23761)** у файлі
  РУБІН для того самого товару ("Напій Fragolino") — сильний натяк, що
  артикул спільний на всі юрособи, а `product_id`/`customer_id` з
  РУБІН-файлу — суто внутрішні ID цієї юрособи.

## 5. Відкриті питання

Заміни `_(твоя відповідь)_` під кожним питанням на свою відповідь.

**Q1. Каталог товарів.** `Product.id_product` має бути спільним
артикулом (`product_articl` / `Код`, той що збігся на прикладі
Fragolino), а не `product_id` з РУБІН-файлу? Чи ESP/OPT/РУБІН взагалі
ведуть єдиний довідник товарів, чи в кожної юрособи свій?
_єдиний довідник товарів для всіх компаній_

**Q2. `Магазин` в ЄСП/ОПТ = клієнт?** Окремого поля клієнта в
`.xls`-файлі нема. Це означає, що водій везе товар із центрального
складу на конкретну точку (склад/АЗС), і саме `Магазин` іде в
`customer_name`/`store` для цього каналу — підтверди.
_у файлі додали назву отримувача в 5 колонку name_store_

> **Уточнення 2026-08-30 (перевірено напряму xlrd на реальному
> оновленому файлі):** новий стовпець з'явився саме 5-ю колонкою, як і
> сказано вище, але буквальна назва заголовка в файлі — `"АЗС"`, не
> `"name_store"` (те було описом по суті, не точним заголовком).
> Значення — `"АЗС Киев Богатирская"` і подібні. `DJANGO_CODING_GUIDE.md`
> Крок 16.4 (`EXPECTED_HEADER`) уже виправлено під це.

**Q3. Номер накладної, який сканує водій, для ЄСП/ОПТ.** Це числова
частина `Докум` (напр. `0000401034` з `"ПеремМежМагазРасх 0000401034"`)?
Чи є десь ще одне поле-ідентифікатор саме "накладної" (те, що фізично
надруковане на папері й сканується QR-кодом)?
_при скануванні водієм отримуємо № в такому форматі `0000401034` - питання до ІТ щоб в колонці був аналогічний формат_

**Q4. Сума продажу для аналітики** (§8 — "% транспортних витрат від
суми продажу"). Це `СуммаР` (роздрібна, вища за `СуммаВх`), а
`СуммаВх`/`ЦенаВх` — собівартість/закупівля? Тобто `line_total` мапиться
на `СуммаР`, а не на `СуммаВх`?
_Сума продажу для аналітики: Рубін - price_invoice (ціна за 1 шт товару) або line_total ; ЄСП та ОПТ - ЦенаВх (ціна за 1 шт товару) або СуммаВх_

**Q5. Службові рядки.** `"ИТОГО:"` в кінці файлу — просто ігнорувати
при імпорті? Чи бувають ще проміжні підсумкові рядки всередині файлу
(не тільки в самому кінці), на які теж треба зважати?
_ігноруємо при імпорті_

**Q6. Формат дати `DD.MM.YY`.** Рік завжди двозначний і завжди означає
20XX (тобто `26` = `2026`), без винятків?
_все вірно `26` = `2026`_

**Q7. Повернення в каналі ЄСП/ОПТ.** У переглянутих даних жодного
від'ємного рядка нема — це тому, що повернення в цьому каналі взагалі
не йдуть через цей файл (інший процес/інша форма), чи просто в цьому
конкретному вивантаженні їх не було й вони МОЖУТЬ трапитись?
_повернення в цьому каналі взагалі не йдуть через цей файл_

**Q8. Юридична особа визначається файлом, не колонкою.** Тобто на
сторінці завантаження менеджер явно обирає, який це файл (РУБІН/ЄСП/ОПТ),
а не система вгадує юрособу з вмісту — підтверди.
_менеджер явно обирає, який це файл (РУБІН/ЄСП/ОПТ)_

**Q9. Точний UX перезавантаження.** Коли менеджер вивантажує файл:
(а) система сама визначає, які дати перезаписати, **на основі дат, що
є у файлі** (видаляємо старі записи саме за ці дати для цієї юрособи,
решту історії не чіпаємо), чи
(б) менеджер додатково вручну вказує дату/діапазон для видалення
окремо від самого файлу (наприклад on текстове поле "перезалити з
2026-08-10 по 2026-08-17")?
_видаляємо старі записи саме за ці дати для цієї юрособи,
решту історії не чіпаємо_

**Q10. Структура ОПТ-файлу.** Чи ОПТ-файл має **точно ту саму** назву
й порядок колонок, що й ЄСП (`Магазин`, `ДатаДок`, `Докум`, `Категория`,
`Код`, `Товар`, `Количество`, `ЦенаВх`, `СуммаВх`, `СуммаР`,
`КоличВупак`, `Вес`), просто з іншими значеннями `Магазин` (~8 АЗС
замість 2 складів)? Якщо так — ЄСП і ОПТ можна парсити одним спільним
кодом, різницю задавати лише параметром `legal_entity`. Якщо структура
хоч трохи відрізняється — краще додати сюди приклад ОПТ-файлу.
_ЄСП і ОПТ одна структура файлу_

**Q11. Прив'язка до `RouteEvent`.** Водій сканує QR і в системі вже є
`RouteEvent.waybill_number`/`waybill_date` (Фаза 3.7). Імпорт із 1С
створює/оновлює `WaybillRecord` за тим самим номером. Чи потрібно
щось робити з `RouteEvent`, коли приходить імпорт (наприклад
підтверджувати/зв'язувати?), чи це вже покрито тим, що обидва
посилаються на однаковий `waybill_number`/`waybill_date`, і окремого
коду для зв'язку не треба?
_обидва посилаються на однаковий `waybill_number`_

**Q12. Розмір файлу і продуктивність.** ЄСП-файл — 39579 рядків,
~7.6 МБ. Скільки приблизно рядків очікується у ЩОТИЖНЕВОМУ вивантаженні
(не за весь час, а саме за тиждень, який менеджер типово заливає) —
кілька сотень, кілька тисяч? Це впливає на те, чи можна робити
синхронний `POST`-запит з обробкою в тому ж request/response циклі, чи
варto одразу закладати фонову задачу (Celery/thread) з прогрес-баром.
_2000 - 4000 рядків_
